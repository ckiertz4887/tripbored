# TripBored

A road trip spotting game. 425 cards across 18 categories — license plates,
vehicles, wildlife, roadside places, family moments. Tap what you see out the
window, rack up points.

**Stack:** Vite + React + TypeScript, Firebase (Auth + Firestore + Hosting).
No separate backend.

If you're working on this with Claude Code, read `CLAUDE.md` first — it has
the durable project context, the constraints that came from real beta
testing, and pointers into `docs/` (original planning doc, beta-test backlog,
and a flat CSV snapshot of the card catalog).

---

## Getting it running

```bash
npm install
cp .env.example .env.local   # fill in your Firebase web config
npm run dev
```

### Firebase setup (one time)

1. Create a project at <https://console.firebase.google.com>.
2. **Build > Authentication > Sign-in method**: enable **Google** and
   **Anonymous**. Anonymous is required — it's how someone opening a shared
   link starts playing without a sign-up wall.
3. **Build > Firestore Database**: create a database in production mode.
4. **Project settings > Your apps > Web**: register an app, copy the config
   values into `.env.local`.
5. Deploy the security rules:
   ```bash
   npx firebase login
   npx firebase use --add          # pick your project
   npx firebase deploy --only firestore
   ```

### Deploy

```bash
npm run deploy      # builds, then pushes to Firebase Hosting
```

By default this publishes to `<project-id>.web.app` / `<project-id>.firebaseapp.com`.
To serve on **tripbored.com** instead:

1. Firebase Console > **Hosting** > **Add custom domain** > enter `tripbored.com`
   (and `www.tripbored.com` if you want that to resolve too).
2. Add the DNS records Firebase gives you at your domain registrar. Firebase
   issues the SSL certificate automatically once DNS verifies — usually
   minutes, occasionally up to 24 hours.
3. Update `authDomain` handling: Google sign-in's redirect works off the
   Firebase `authDomain` in `.env.local`, not the custom domain, so no code
   change is needed here — just the DNS step above.

## How the pieces fit

### Offline-first

This game is played in exactly the places where cell service dies. Firestore is
initialized with `persistentLocalCache`, so every tap writes to IndexedDB
immediately and syncs when service returns. **Nothing in the UI ever waits on
the network.** Reads stream from the local cache first, so reopening a trip in a
dead zone shows the full board instantly.

This is also why the game works if you navigate away mid-trip — state lives in
Firestore (locally cached), not in component state.

### Sharing model

A game's id *is* its permission. Ids are 16 random characters, so a URL is
unguessable, and anyone who has one can open the game and contribute. There's
no invite flow, no join codes — you send the link, they tap cards.

Opening a shared link signs you in anonymously and adds you to the game's
members, so your taps carry your name and the trip shows up in your history
later. Signing in with Google afterwards *links* to the same uid, so a guest
who decides to make an account keeps everything they already did.

Only the owner can rename or finalize. This is enforced in `firestore.rules`,
not just hidden in the UI.

### Data model

```
users/{uid}                      profile, lifetime totals
games/{gameId}                   name, ownerUid, status, memberIds, members
games/{gameId}/finds/{cardId}    one doc per found card — points, who, when
games/{gameId}/events/{eventId}  append-only tap/untap log, powers undo
```

Score is always recomputed from `finds`, never incremented. That's deliberate:
it's why untapping correctly subtracts points, and why two people tapping at
once can't corrupt the total.

The `events` log is append-only and never deleted, so the full history of a
trip — including accidental taps that were undone — stays intact.

### The card catalog

`src/data/cards.ts` is generated by `scripts/build-cards.mjs` from
`scripts/card-catalog.mjs` — that second file is the actual source of truth
for every card, name, and point value. To change the catalog:

```bash
# edit scripts/card-catalog.mjs, then:
npm run build:cards
```

Never hand-edit `src/data/cards.ts` — the header says so, and the next
regeneration overwrites it silently. A card's `id` is derived from its name,
so **renaming a card changes its id** and orphans existing finds — if you
rename cards after people have played, write a migration.

`docs/card-catalog-reference.csv` is a flat snapshot of the same data for
reviewing outside the codebase — it's a reference copy, not a source; edits
there don't do anything until ported back into `card-catalog.mjs`.

### Scroll vs. tap

`CardTile` uses pointer events with a 10px movement threshold rather than
`onClick`. If the pointer drifts more than that between down and up, the
gesture was a scroll and the card doesn't flip. This fixes the beta finding
that scrolling the board was registering as card taps.

## Not built yet

Deliberately left for later, in rough priority order:

- **Route-aware plate scoring** — the gravity model. Plates are flat 5s today.
- **Bonus rounds and mini-games** — billboards, brands, trivia, word games.
- **Trip photo + share card** — a branded summary image on finalize.
- **GPS tagging** — tap-and-hold to attach where a card was spotted.
- **Versus mode** — teams/cars competing rather than one shared board.
- **Stats and insights** — beyond the lifetime totals on the profile page.
- **Plate version gallery** — the per-state alternate-design counter.
